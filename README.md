## Интеллектуальная система внутренней технической поддержки 

pet-проект корпоративной IT-платформы, которая
помогает сотрудникам получать техническую поддержку, находить ответы во
внутренней документации и передавать сложные инциденты специалистам.

### 1. Цели проекта
- Создать работающий портал внутренних IT-обращений.
- Реализовать AI-помощника, который классифицирует обращения и
  предлагает следующие шаги.
- Построить корпоративную базу знаний с поиском на основе RAG и
  ответами со ссылками на источники.
- Подключить безопасные диагностические инструменты через API и MCP.
- Автоматизировать маршрутизацию заявок и уведомления.
- Развернуть приложение в контейнерах и обеспечить наблюдаемость его
  работы.
- На практике изучить архитектуру приложений, Linux, сети, Docker,
  CI/CD и мониторинг.
### 2. Пользователи и роли
- Сотрудник: создаёт обращение, общается с AI-помощником,
  просматривает свои заявки и инструкции.
- Специалист поддержки: просматривает очередь обращений, уточняет
  диагностику, назначает приоритет и исполнителя, меняет статус и
  фиксирует решение.
- Администратор: управляет пользователями, ролями, источниками
  документации, интеграциями и настройками.
- AI-компоненты: классифицируют обращения, извлекают контекст,
  ищут документы и вызывают только разрешённые инструменты.

# Основные сценарии работы
### Сценарий A. Самостоятельное решение проблемы через базу знаний
1. Сотрудник открывает чат и описывает проблему: «Не получается
   подключиться к VPN».
2. Backend передаёт запрос AI-модулю.
3. RAG-компонент ищет релевантные фрагменты в утверждённой
   документации.
4. LLM формирует ответ на основе найденных материалов.
5. Интерфейс показывает инструкцию и ссылки на документы-источники.
6. Сотрудник отмечает, помогло ли решение.
Результат: сотрудник получает ответ без создания заявки, если
проблема решена.
### Сценарий B. Создание и классификация заявки
1. Сотрудник описывает проблему и отправляет обращение.
2. Backend сохраняет заявку и присваивает ей идентификатор.
3. AI-модуль предлагает категорию, краткое описание и предварительный
   приоритет.
4. Сотрудник может проверить и исправить предложенные значения.
5. Заявка появляется в очереди поддержки.
Результат: обращение структурировано, но AI не подменяет сотрудника
и не принимает критичные решения без контроля.
Сценарий C. Диагностика инцидента
1. Сотрудник сообщает, что внутренний сайт возвращает ошибку 502.
2. AI определяет, что нужна диагностика доступности сервиса.
3. При наличии разрешений агент вызывает безопасный инструмент проверки
   HTTP endpoint.
4. При необходимости получает ограниченную выборку технических логов.
5. RAG ищет инструкции по соответствующему сервису и типу ошибки.
6. AI составляет гипотезы, указывает использованные данные и предлагает
   дальнейшие шаги.
7. Опасные действия (перезапуск, изменение конфигурации, удаление
   данных) недоступны агенту либо требуют явного подтверждения
   уполномоченного специалиста.
Результат: специалист получает собранный контекст, а не только текст
жалобы.
Сценарий D. Передача заявки специалисту
1. AI понимает, что не может надёжно решить проблему.
2. Backend создаёт или обновляет заявку.
3. Правила маршрутизации выбирают очередь или группу поддержки.
4. Оркестратор отправляет уведомление.
5. Специалист видит описание, категорию, историю диалога, найденные
   документы и результаты разрешённой диагностики.
Результат: сложный случай передан человеку с сохранением контекста.
Сценарий E. Автоматизация через внешние системы
1. В системе появляется новая заявка.
2. Backend отправляет событие в n8n через webhook.
3. Workflow проверяет тип обращения и запускает нужную
   последовательность.
4. При необходимости создаётся задача в GitHub Issues или отправляется
   уведомление.
5. Результат интеграции возвращается в backend и фиксируется в истории
   заявки.
Результат: повторяющиеся административные операции автоматизированы.
Сценарий F. Управление корпоративной базой знаний
1. Администратор добавляет документ или подключает источник.
2. Сервис индексации извлекает текст и метаданные.
3. Текст разбивается на фрагменты (chunks).
4. Embedding-модель преобразует фрагменты в векторы.
5. Векторы и метаданные сохраняются в векторной БД.
6. При обновлении документа его индекс переобрабатывается.
Результат: AI-помощник использует актуальную документацию и может
ссылаться на источники.
Сценарий G. Контроль состояния платформы
1. Сервисы публикуют метрики и структурированные логи.
2. Prometheus собирает метрики, Loki принимает логи.
3. Grafana отображает состояние приложения и инфраструктуры.
4. При превышении порогов создаётся alert.
5. Информация об инциденте может быть передана в систему заявок.
Результат: неисправности самой платформы обнаруживаются до массовых
обращений пользователей.

Потоки данных
Поток обращения: Web UI → FastAPI → Ticket Service → PostgreSQL.

Поток AI-ответа: FastAPI → AI Service → RAG retrieval → Qdrant →
найденные фрагменты → LLM → ответ с источниками.

Поток диагностики: AI Agent → MCP Client → MCP Server → разрешённый
инструмент → результат → AI Agent. Инструменты должны иметь минимально
необходимые права.

Поток автоматизации: Backend Event/Webhook → n8n → внешняя система →
callback/API → Backend.

Поток наблюдаемости: сервисы → метрики и логи → Prometheus/Loki →
Grafana/Alerting.

6. Данные и основные сущности
Предварительные сущности реляционной БД:
- users --- пользователи и роли;
- tickets --- заявки, категория, приоритет, статус, назначенная
  группа;
- ticket_messages --- сообщения и комментарии;
- ticket_events --- история изменения статусов и действий;
- knowledge_sources --- источники документации;
- documents --- документы и версии;
- integrations --- конфигурации подключённых систем (секреты
  отдельно);
- ai_runs --- метаданные запусков AI, модель, время выполнения,
  результат и статус.
В Qdrant хранятся векторы фрагментов документов и необходимые
метаданные: идентификатор документа, версия, заголовок, источник, права
доступа и номер фрагмента.
7. Безопасность и ограничения
- Аутентификация и ролевая модель доступа.
- Проверка прав на документы до выдачи найденных фрагментов
  пользователю.
- Секреты и токены не хранятся в Git и не попадают в логи.
- MCP-инструменты работают по принципу минимальных привилегий.
- Диагностические инструменты по умолчанию read-only.
- Любые изменяющие инфраструктуру операции требуют отдельного
  разрешения и подтверждения.
- Внешние документы и содержимое тикетов считаются недоверенными
  данными, а не инструкциями для AI.
- Логи не должны содержать пароли, токены и избыточные персональные
  данные.
- Для демонстрации используются вымышленные пользователи, документы и
  инфраструктурные события.

9. Что измерять
- Доля заявок, правильно классифицированных AI.
- Качество поиска документов: Recall@k и MRR на тестовом наборе.
- Доля ответов, подтверждённых релевантными источниками.
- Время ответа LLM и полного запроса.
- Доля успешно выполненных интеграций.
- Количество ошибок API.
- Доступность сервисов и потребление ресурсов.
- Доля обращений, решённых без передачи специалисту (только как
  продуктовая метрика, не как единственный критерий качества).
10. Репозиторий и процесс разработки
Работа ведётся через GitHub:
- Issues: отдельные задачи на функции, исправления, исследования и
  технический долг.
- Projects: доска для планирования и отслеживания этапов.
- Branches: отдельная ветка на задачу.
- Pull Requests: обсуждение и проверка изменений перед слиянием.
- Actions: автоматический запуск тестов и проверок.
Пример названий Issues:
- feat: создать модель заявки
- feat: добавить API создания тикета
- research: сравнить локальные embedding-модели
- feat: реализовать индексацию Markdown-документов
- test: добавить тесты поиска RAG
- ops: настроить резервное копирование PostgreSQL
11. Критерии готовности проекта
Проект можно считать завершённым в портфолио, когда:
1. Пользователь может создать заявку и отслеживать её статус.
2. AI классифицирует заявку и объясняет результат.
3. Пользователь может задать вопрос по документации и получить ответ с
   источниками.
4. Специалист может просмотреть историю и результаты диагностики.
5. Интеграции выполняются с обработкой ошибок и аудитом.
6. Приложение развёрнуто воспроизводимым способом.
7. Есть мониторинг, резервное копирование и базовые меры защиты.
8. README, схема архитектуры, инструкции запуска и демонстрационные
   данные доступны в репозитории.
Принцип разработки: сначала надёжный работающий продукт, затем
AI-функции, затем интеграции и эксплуатационная зрелость. Каждая
технология должна решать конкретную задачу, а не добавляться ради
количества инструментов в резюме.
